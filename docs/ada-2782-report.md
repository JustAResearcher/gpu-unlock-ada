# RTX 4070 Ti (10de:2782) Ada canary on Linux

On October 24, 2026, the AD102-family four-PLM payload ran on one RTX 4070 Ti
(`10de:2782`, AD104, 60 SMs, ASUS board `1043:88dd`, VBIOS `95.04.3C.80.6E`).
It ran before the unmodified NVIDIA `595.99.02` open kernel module, inside a KVM
guest with the card passed through by VFIO. Every gate the module enforces
passed. The NVIDIA RM getter changed FMLA32, IMLA2 and IMLA4 from half to full
rate. Matched stock and unlocked runs on the same card, driver, binaries and
285 W cap measured about 2x FP16/BF16/TF32 FP32-accumulate instruction rate.
They measured +93% to +94% on large cuBLAS GEMMs, with zero numerical failures.

This is one physical card and one cold boot. It does not establish support for
other AD104 boards, for the RTX 4070 or 4070 SUPER, or for bare-metal hosts. It
also does not establish how the same board behaves on a warm reboot without VFIO.
The [evidence directory](evidence/ada2782/README.md) contains the boot messages,
rate readbacks and unedited benchmark stdout, with the GPU UUID replaced.

This is the Linux counterpart of the separate
[Windows UEFI AD104 port](ad104-windows-latence-app.md), which ran on an MSI
board. The Linux module needs no board pin. It reads FWSEC-FRTS from the
card's own PROM, and this ASUS ROM parsed without changes (four-image chain,
FWSEC signature versions `0x3`, fuse version 1).

## Host and guest

- Host: Proxmox VE, kernel `6.8.12-9-pve`. `vfio-pci` binds `10de:2782` at
  boot, and `nvidia`/`nouveau` are blacklisted, so no host driver touches the card.
  The card links at PCIe Gen4 x8.
- Guest: Ubuntu 24.04.4, SeaBIOS, kernel `6.8.0-147-generic`,
  `nvidia-driver-595-open` `595.99.02`. The guest sees the card at
  `0000:00:10.0`.
- Module: built from this branch against the guest kernel with Kbuild, not DKMS.
  It is unsigned, which taints the kernel. Its `.ko` hash is build-specific and
  not recorded.
  - installed to `updates/`
  - loaded from the initramfs-tools image, with `softdep nvidia pre: gpu_unlock`
  - firmware generated by `make firmware` from the pinned 610.43.03 inputs, all
    hashes matching
- Command line:
  `gpu_unlock.targets=0000:00:10.0 gpu_unlock.ad104_experimental=1`.
- Cold boot: the host was shut down to soft-off and started again from its
  power button. The guest then started for the first time since power-on.
  The module's entry readback reported WPR2 high `0x0`. AC was not removed.

`make test-full` passed 29 tests (3 optional PyCryptodome skips) with the
generated assets, including the new AD104 gating, asset-selection and mocked
dispatch cases.

## Firmware and driver checks

The kernel log recorded:

- entry: `PLM=0xffffff8f`, `SS0=0x4022015`, `SS1=0x5`, WPR2 high `0x0`,
  chip `0x194000a1`;
- FWSEC-FRTS result scratch `0x0`, WPR2 `0x2ff8000`–`0x2ff8e00` at the expected
  page;
- payload marker `0x67b00001` (expected `0x67b00001`), SEC2 halted;
- the three required permission writes: `WPR_CFG=0xfffff0ff`,
  `WPR=0xffffffff`, `FEAT=0xffffffff`. The observational FBPA field stayed
  `0xffffff0f`, as on the 2705 and 2805;
- selector writes read back `SS0=0x88888888` and `SS1=0x8`. The effective
  readout changed from fields `0 0 2 0 0 2 0 2 0` to all zero;
- after PCIe FLR: GFW `plm=0x8b8f boot=0x3ff cpuctl=0x10`, GSP halted, BME
  clear, selectors still `SS0=88888888 SS1=00000008`;
- `gpu_unlock: unlocked`.

The post-FLR GFW values and entry PLM match the MSI Windows port's pinned
expectations. Entry `SS1` was `0x5`, where the Windows port requires `1`.
The Linux module does not gate on entry selector values.

The stock driver then loaded, and CUDA and cuBLAS work completed. Neither boot's
kernel log contained an NVRM Xid or GPU-fallen-off message.

The read-only RM getter reported:

| Field | Stock | Unlocked |
| --- | ---: | ---: |
| FMLA32 | 1 (half) | 0 (full) |
| IMLA2 | 1 (half) | 0 (full) |
| IMLA4 | 1 (half) | 0 (full) |
| IMLA0, FMLA16, DP, FFMA, IMLA1, IMLA3 | 0 | 0 |

The stock reading was taken in an earlier boot of the same guest, before this
build was installed.

## Guest reboot without host power-off

The guest was then rebooted with the same command line while the host stayed
powered. VFIO resets the device across guest restarts. The module logged
`entry: plm=0xffffffff ss0=0x88888888 ss1=0x8 wpr2_hi=0x0` and returned
`-EALREADY` (`-114`) without starting firmware. The RM getter still reported
every field at full rate, so the unlock persisted across the guest reboot and
its device reset. Only one such reboot was tested.

## Matched throughput

All runs used the same card, guest kernel, driver and 285 W cap, and the same
binaries (built with CUDA 12.0 for `sm_89`, hashes in
`evidence/ada2782/bench-binaries.sha256`).

`diagnostics/bench/mma_bench.cu`, 20,000 iterations, five repetitions, best
TF/s:

| Mode | Stock | Unlocked |
| --- | ---: | ---: |
| FP16 → FP16 | 169.4 | 170.0 |
| FP16 → FP32 | 84.8 | 169.4 |
| BF16 → FP32 | 84.7 | 168.9 |
| S8 → S32 | 338.8 | 338.0 |
| DP4A | 84.1 | 84.0 |
| FFMA | 40.1 | 40.2 |

`tensor_modes_issue.cu` (cubin SHA-256
`fc0efe680a13f58979af9c786bd586fb7e11abcf4e69390de9d90dd27ac599d4`), three
repetitions, best rate, 0 / 270,336 mismatches in every mode:

| Mode | Stock | Unlocked |
| --- | ---: | ---: |
| FP16 → FP32 | 84.8 TF/s | 168.0 TF/s |
| TF32 → FP32 | 42.4 TF/s | 84.0 TF/s |
| Unsigned INT4 → INT32 | 673.9 TOP/s | 672.4 TOP/s |

The matched-report cuBLAS GEMM (`docs/evidence/rtx4090-pr1-stock/gemm_bench.cu`),
median TF/s over five repetitions, every output cell checked, zero failures:

| Shape | Mode | Stock | Unlocked | Change |
| --- | --- | ---: | ---: | ---: |
| 1024³ | FP16/FP32 | 51.9 | 77.8 | +50% |
| 1024³ | BF16/FP32 | 51.9 | 78.0 | +50% |
| 4096³ | FP16/FP32 | 79.8 | 154.0 | +93% |
| 4096³ | BF16/FP32 | 79.6 | 153.4 | +93% |
| 8192³ | FP16/FP32 | 83.4 | 162.1 | +94% |
| 8192³ | BF16/FP32 | 83.4 | 161.2 | +93% |

`validate_gemm.cu` passed all six seeded FP16/BF16 cases with zero failures
and zero maximum absolute error in both states.

Point telemetry at 100 ms, samples above 150 W only:

| | Median SM clock | Lowest SM clock | Median power | Peak power | Peak temperature |
| --- | ---: | ---: | ---: | ---: | ---: |
| Stock | 2,820 MHz | 2,820 MHz | 177 W | 184 W | 59 C |
| Unlocked | 2,775 MHz | 2,760 MHz | 214 W | 221 W | 68 C |

These are short-run point samples. They do not establish long-term thermals or
power behaviour.

One application data point: a mixture-of-experts LLM inference engine
(quantized weights, CPU/GPU split) showed about +3–4% prompt processing and
unchanged decode. That is one unlocked repetition against thirteen stock
repetitions on the same host configuration. It is not part of the evidence set.
